# 项目一 · MCP 工具网关（Tool Gateway）

手写 MCP 协议层 + 多 Server 工具网关：把"给 Agent 供工具"从"调个 SDK"做成能讲清协议、能控权限、能审计、能量化的工程系统。

**当前状态：可运行、可测量、可提交。** 4 个 Server / 12 个 Tool / 45 个单测 / 12 例红队全过 / 真实外部 API 带缓存。零第三方依赖。

```bash
python demo.py                            # 7 个场景，全部断言
python -m unittest discover -s tests      # 45 个单测，离线可跑
python bench.py all --out result.json     # 出数字
```

---

## 1. 一个信息差（面试时最好用的一句）

MCP 规范在 **2026-07-28** 做了大改：

| 改动 | 旧（≤ 2025-11-25） | 新（2026-07-28） |
|---|---|---|
| 会话 | `initialize` + `notifications/initialized` | **取消握手，完全无状态** |
| 版本协商 | 握手时谈一次 | **每个请求在 `_meta` 里自带版本** |
| 服务发现 | 无 | **必须实现 `server/discover`** |
| 结果结构 | 无统一标记 | 所有 result 必须带 `resultType` |
| 未知版本 | `-32602` | 专用错误码 **`-32022`** |

本实现是 **dual-era**：先用 `server/discover` 探测现代服务端，收到不支持的信号再回退到 `initialize`。两条路径都有单测（`mcp_min/server.py`）。

市面上绝大多数教程还停在旧握手。这个差异只要说出"7 月改版把会话去掉了"，就足以区分"照着教程抄"和"读过规范"。

## 2. 架构

```
                     ┌──────────────────────────────────────────┐
   模型 / LangGraph → │  clients/  名字映射 · 轨迹 · 审批回调      │
                     └──────────────────┬───────────────────────┘
                                        │ OpenAI function schema
                     ┌──────────────────▼───────────────────────┐
                     │  gateway/  聚合 · 命名空间 · 风险分级      │
                     │            审批门 · 审计 · 预算 · 截断     │
                     └───┬──────────┬──────────┬──────────┬─────┘
                    stdio│     stdio│     stdio│     stdio│
                  ┌──────▼──┐ ┌─────▼────┐ ┌───▼─────┐ ┌──▼──────┐
                  │ campus  │ │ library  │ │ notice  │ │ github  │
                  │ SQLite  │ │ SQLite   │ │ SQLite  │ │ REST API│
                  └─────────┘ └──────────┘ └─────────┘ └────┬────┘
                                                            │缓存/ETag/降级
                                                     datasource/github_api.py
```

- **`mcp_min/`** 协议层：JSON-RPC framing、双时代 dispatch、最小 JSON Schema 校验。零依赖。
- **`datasource/`** 数据层：SQLite 校园库 + 真实 GitHub REST 客户端（磁盘缓存、ETag、限流降级）。
- **`servers/`** 4 个 MCP Server，共 12 个 Tool，含读写两类。
- **`gateway/`** 核心原创部分：策略、审批、审计、预算、截断、进程自愈。
- **`clients/`** 接入层：`. → __` 名字映射、带审批中断的 Agent 循环、成本核算。

## 3. 实测数据（2026-11-01）

### 3.1 基础设施

| 指标 | 结果 | 怎么测的 |
|---|---|---|
| Server / Tool 数 | 4 / 12 | `demo.py` 场景 1 |
| 单测 | **45 通过** | `unittest discover` |
| 红队拦截率 | **100%（12/12）** | 参数注入 / 描述投毒 / 伪造版本 / 预算 / 截断 |
| 网关延迟 | **P50 16.0ms，P95 18.7ms** | 30 次 `tools/call`，本地 stdio，含鉴权+审计落盘 |
| 端到端轨迹 | **4/4 通过**，7 次工具调用，平均 33.2ms | scripted 模型，覆盖 允许/拒绝/审批 三条分支 |
| 外网缓存 | 冷 **735.8ms** → 命中 **10.8ms**，**68×** | GitHub `search/issues`，冷=ttl 0，热=ttl 24h |

### 3.2 工具选择准确率（真模型，63 条自建用例，12 个工具）

| 模型 | 原描述 | 改写描述 | 变化 |
|---|---|---|---|
| deepseek-flash | 77.8% (49/63) | **92.1% (58/63)** | **+14.3 pt** |
| deepseek-v4-pro | 79.4% (50/63) | **100% (63/63)** | **+20.6 pt** |

配对检验（McNemar，同一批 63 条）：flash 修正 10 条、改坏 1 条，**p=0.0117**；v4-pro 修正 13 条、改坏 0 条，**p=0.0002**。不是噪声。

> **v4-pro 的 100% 请谨慎引用**：同一配置跑过两次，分别是 62/63 和 63/63。7 亿参数的差异不该被当成确定性结论，`92%~100%` 才是诚实区间。

### 3.3 工具数量衰减（flash，同一模型同一描述）

| 可见工具数 | 原描述 | 改写描述 |
|---|---|---|
| 3 | 100% (17/17) | 100% (17/17) |
| 6 | 89.2% (33/37) | **100%** (37/37) |
| 9 | 84.0% (42/50) | 92.0% (46/50) |
| 12 | 77.8% (49/63) | 92.1% (58/63) |

原描述下，工具从 3 个加到 12 个，准确率掉 **22.2 个百分点**；改写描述后只掉 **7.9 个百分点**。**好的工具描述把"工具一多就选错"这个衰减压掉了约三分之二。**

### 3.4 这三个数字放在一起才有意义

```
换更大的模型：  77.8% → 79.4%   （+1.6 pt，不显著）
改写工具描述：  77.8% → 92.1%   （+14.3 pt，p=0.0117）
```

**瓶颈不在模型，在工具描述。** 而"换模型"是最贵、最慢、最容易被想到的那条路。先做便宜的对照实验，再决定要不要花钱——这是工程判断，不是调参。

原描述下 14 条错误里，**13 条是同一种形状**：模型把写操作选成了它的只读兄弟。

```
submit_course_change → search_courses      （我要选 CS401）
borrow_book          → search_books        （帮我借一下 TP391-12）
comment_issue        → get_issue           （回复他我们会跟进）
```

原因很具体：用户说了"借一下 TP391-12"，而 `search_books` 的描述是"检索馆藏，返回索书号"——用户给的正是一个索书号，模型于是理解为"先查一下"。**描述里没有一句话告诉它"什么时候不要用我"。**

改写后的描述只加了三样东西（全文见 `benchkit/descriptions.py`）：

1. **【只读】/【写入】** 前缀——读写属性在读完整段描述之前就可见；
2. **负向约束**——"仅用于查找；用户要借出时改用 `library.borrow_book`，即使他已经给出索书号"；
3. **用户原话当触发词**——"借一下 / 退掉 / 回一条"，因为路由器匹配的是表面形式，不是本体。

> **改进版目前没有合入 `servers/` 里的原始定义**，只作为 `--describe improved` 这一实验臂存在。这是故意的：一旦合入，原描述就没有对照组了，数字也就不可复现。正确的收尾方式是给工具描述加一条 lint（检查每个 write 工具是否有排他指向、每个 read 工具是否声明了"不要用它做什么"），在 CI 里拦住回退——这是下一步，还没做。

### 3.5 附带发现：`required` 会诱发幻觉工具名

`tool_choice=required` 逼模型必须选一个，选不出来时它会**编一个工具名**。63 条里出现过一次：`name_placeholder`。网关侧对"未知工具名"仍走 `_authorize` 拒绝，但接入层必须在返回前校验名字是否在 `tools` 名单里。这条已写进 `benchkit/llm.py`。

### 3.6 另一条容易误读的曲线：`tool_choice=auto`

同 63 条用例、`auto` 模式下准确率只有 53.6%（15/28 那批，28 条版本）。逐条看失败原因，绝大多数不是选错工具，而是**模型反问**：

> 用户："我上学期考了多少分"
> 模型："我需要先确认你的学号才能查询成绩，请提供学号（7–12 位）"

参数不全时追问，是正确行为，但被"是否选对工具"这个单一指标判成了错误。**指标设计本身会影响结论**——这条留到项目四（评测层）展开。

### 3.7 复现命令

```bash
export BENCH_API_KEY=sk-xxx                     # DeepSeek 即可，全部实验约 ¥0.5
export BENCH_MODEL=deepseek-flash

python bench.py select --provider openai --thinking off --tool-choice required \
       --limit 12 --describe original --out a.json    # 77.8%
python bench.py select --provider openai --thinking off --tool-choice required \
       --limit 12 --describe improved --out b.json    # 92.1%
```

`--limit 3/6/9/12` 画衰减曲线，`--describe original/improved` 切描述组。`--out` 会记录每次调用的 token 数（flash 原描述 1605 tokens/次，改写后 1847，+15% 是描述变长的代价）。

## 4. 五个能撑住追问的设计决策

**① 风险表放在网关，不信 Server 的 `annotations`**
规范原文写明 annotations 不可信。红队用例 `poisoned_annotation` 让 Server 谎称写工具是只读——网关按自己的注册表判定为 `admin`，直接拒。这是"工具投毒"最直接的防线。

**② 截断保留头尾，并显式标注**
只砍后半段会让模型以为自己读到了完整内容，然后自信地编。测试与演示都在验证这一点。
**连带发现**：把 JSON 文本截断后它就不可解析了，所以需要机器可读结果的地方必须读 `structuredContent`（协议里专门为此存在）。`demo.py` 场景 4 就演示了这个坑。

**③ 审批是"暂停"，不是"失败"**
`ApprovalRequired` 在循环里被 `on_approval` 回调接住，用户同意后**带 `approved=True` 重放同一调用**，轨迹不断裂；拒绝则回一条"换种做法"的工具消息给模型，不终止任务。

**④ 外网工具必须能降级**
无鉴权 GitHub 每小时 60 次。天真实现会在 403 时抛错，把整条轨迹拖死。这里：磁盘缓存 + ETag 304 + 限流时返回 `stale` 缓存并把降级原因写进 `_meta`，模型能看到"这是旧数据"而不是"失败了"。

**⑤ 看不到的工具也走鉴权**
模型只能看到 `list_tools` 返回的工具，但循环里对"未知名字"仍做 `__ → .` 还原后走一遍 `_authorize`。多一层判断，避免幻觉工具名绕过策略层。

## 5. Difference from upstream

协议层参考 MCP 规范 `2026-07-28` 手写，**未使用**官方 SDK（`modelcontextprotocol/python-sdk`）或 FastMCP：

1. **双时代支持**：官方 SDK 面向单一协议版本；本实现用 `server/discover` + 错误码回退，同时服务无状态新客户端与 legacy `initialize` 客户端。
2. **网关层为原创**：多 Server 聚合、命名空间消歧、风险分级、审批门、审计、预算、进程自愈，上游均无对应实现。
3. **风险表独立于服务端声明**：依据规范"annotations 不可信"的要求。
4. **截断策略**：保头保尾 + 显式标记，而非丢弃尾部。
5. **缓存与降级**：`datasource/github_api.py` 自行实现 ETag/304、限流兜底、离线 stale，未引入 `requests`/`httpx`。
6. **简化项**：未实现 `subscriptions/listen`、MRTR（`input_required`）、Streamable HTTP 传输与 OAuth；仅覆盖 stdio。

### 三个最可能被追问的点

**Q：92.1% 有多少是过拟合？**
A：描述是照着这 63 条的错误改的，确实有过拟合风险。可验证的旁证是**工具数衰减曲线被压平了**（6 个工具时 89.2%→100%，说明修正的是通用机制而非个例），以及 pro 模型在完全相同的描述下从 79.4% 到 100%——两个独立信号同向。要彻底排除，需要一份改描述时没看过的留出集，这是我下一步要做的。

**Q：为什么不用 12 个工具直接测，非要画 3/6/9/12 的曲线？**
A：单个数字只能说明"行不行"，曲线能说明"什么时候开始不行"。3 个工具时 100%，说明基础能力没问题；掉到 77.8% 说明是工具数量在起作用。**没有曲线，就看不出这是个规模化问题。**

**Q：这个项目最难的部分是什么？**
A：不是协议层，是**确定该测什么**。一开始我只测"12 个工具下准确率多少"，得到 85.7%，然后就卡住了——不知道该往哪改。直到把 14 条错误逐条打印出来，发现 13 条是同一个形状（写操作被选成只读兄弟），才找到可以下手的地方。**先看错误分布，再想改进方案**，这个顺序比任何技巧都重要。

## 8. 已知局限（主动说）

- 只实现 stdio，未做 Streamable HTTP 与鉴权
- 未实现 `subscriptions/listen` 与 MRTR，长任务靠超时兜底
- 风险表是静态配置，未做动态学习
- 单进程串行调用，未做并发调度
- **选择基准只有 63 条，且描述改写是看着这 63 条的错误做的**——存在过拟合风险，正解是留一份改描述时没看过的留出集
- 63 条里每条工具约 5 条用例，单一工具（如 `comment_issue`）的失败率置信区间仍然很宽
- 只用 DeepSeek 两个模型验证，结论能否外推到 GPT / Claude 未验证
- 同一配置重复运行会有 ±1 条波动（见 3.2 的 62/63 与 63/63），单次 100% 不可当结论
- 工具选择基准的 mock provider 只是关键词打分，不是模型

## 10. 环境

Python 3.10+，零第三方依赖。可选环境变量：

| 变量 | 作用 |
|---|---|
| `GITHUB_TOKEN` | 提高 GitHub 限流额度（60/h → 5000/h） |
| `GITHUB_WRITE=1` | 允许 `comment_issue` 真正写入（默认 dry-run） |
| `BENCH_API_KEY` / `BENCH_BASE_URL` / `BENCH_MODEL` | 测真模型的工具选择准确率 |
| `CAMPUS_DB` | 指定另一个 SQLite 路径（测试用） |
